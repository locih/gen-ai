# ADR-007: офлайн-кэш на SQLite WAL

ADR-007: офлайн-кэш на SQLite WAL

Контекст и предпосылки

Мобильное приложение «ФинУчёт» ориентировано на сценарии нестабильного соединения и работу в условиях ограниченной сети. Текущая реализация синхронизации данных требовала постоянного подключения к серверу, что приводило к блокировке интерфейса при потере связи. Для обеспечения непрерывной работы пользователя принята архитектура offline-first, при которой все операции записи и чтения выполняются локально, а синхронизация с сервером происходит асинхронно. Основным хранилищем выбран SQLite WAL на устройстве — механизм журнала с опережающей записью (Write-Ahead Logging), обеспечивающий конкурентный доступ на чтение без блокировок.

Выбор SQLite WAL обусловлен несколькими факторами. Во-первых, WAL-режим позволяет выполнять одновременное чтение и запись без взаимных блокировок, что критично для фоновой синхронизации при активной работе пользователя. Во-вторых, этот режим сокращает количество операций fsync, что снижает нагрузку на flash-память. В-третьих, SQLite WAL на устройстве даёт возможность атомарно применять транзакции, что упрощает обработку сбоев при синхронизации.

Ограничения и управление размером

Для предотвращения неконтролируемого роста базы данных установлен лимит базы 50 МБ. Превышение этого порога обрабатывается автоматически: при попытке записи, которая приведёт к превышению лимита, система инициирует сжатие и очистку устаревших записей. Механизм очистки основан на метках времени последней синхронизации — удаляются записи, которые были успешно переданы на сервер более 30 дней назад. Если после очистки размер базы не уменьшается до 45 МБ, приложение уведомляет пользователя о необходимости ручной архивации данных.

Лимит базы 50 МБ выбран эмпирически на основе типового объёма операций за 90 дней активного использования. Для пользователей с интенсивным трафиком предусмотрена возможность расширения лимита через настройки приложения до 200 МБ, но это требует подтверждения через системный диалог. Важно отметить, что SQLite WAL на устройстве не использует сжатие на уровне файловой системы, поэтому фактический размер базы может превышать логический объём данных из-за служебных записей журнала.

Синхронизация и миграции

Архитектура offline-first подразумевает, что синхронизация при появлении сети запускается автоматически и без участия пользователя. Алгоритм синхронизации двухфазный: сначала отправляются все локальные изменения, затем загружаются обновления с сервера. Для разрешения конфликтов используется правило «последняя запись побеждает» с дополнительной проверкой целостности данных на уровне сущностей. Синхронизация при появлении сети активируется через BroadcastReceiver, слушающий события ConnectivityManager, и имеет приоритет над фоновыми задачами.

Процесс синхронизации также включает проверку версии схемы базы данных. Все миграции выполняются через Room schema v14, которая фиксирует структуру таблиц, индексов и триггеров на момент текущего релиза. Room schema v14 включает поддержку вложенных объектов и полей с типом List, что ранее требовало отдельных таблиц-связок. Миграции через Room schema v14 применяются автоматически при первом запуске после обновления приложения, при этом все операции обёрнуты в транзакцию с откатом при ошибке. Если миграция не может быть выполнена (например, из-за несовместимости данных), приложение блокирует запуск до принудительной очистки кэша пользователем.

Заключение и риски

Принятое решение использовать SQLite WAL на устройстве с лимитом базы 50 МБ полностью соответствует стратегии offline-first. Синхронизация при появлении сети и миграции через Room schema v14 обеспечивают согласованность данных без потери производительности. Ключевые риски: возможное замедление работы при достижении лимита базы и необходимость ручного вмешательства при сбоях миграции. Для минимизации этих рисков введён мониторинг размера базы с предупреждением при 80% заполнения, а также автоматическое тестирование миграций на этапе CI.
