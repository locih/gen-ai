# L1 Helpdesk Copilot - отчёт

## Про что задача

Есть поток IT-тикетов на русском (helpdesk). Нужно автоматически:
1. **Классифицировать** обращение - в какую команду / категорию оно попадает;
2. **Кратко описать** суть (summary);
3. **Выдать план действий** для оператора - что уточнить, куда эскалировать, с опорой на базу знаний.


## Что использовалось

| Техника | Зачем |
|---------|--------|
| **Structured output** (`response_model` + `max_retries`) | Ответ LLM сразу в JSON/Pydantic - не парсим текст руками, при ошибке схемы автоматический retry |
| **field_validator** | Жёсткие правила на выходе: summary не короче 10 символов, шаги по порядку |
| **IE (извлечение)** | Из тикета тянем системы, priority, summary - дальше ими же ищем в KB |
| **Hybrid RAG** (Chroma + BM25 + RRF) | Ищем в базе знаний похожие тикеты и получаем информацию |
| **Ghost-check цитат** | Проверка, что quote из шага реально есть в retrieved-контексте - ловим выдуманные «цитаты из runbook» |
| **LLM-ревизор** (критик + judge) | Один приём - вторая модель оценивает ответ. **Критик** в пайплайне: ok/issue → до 2 rework, без gold. **Judge** на eval: score + сравнение с gold |
| **Правила поверх LLM** (`_normalize_category`) | Изменяем категорию, если есть ключевые слова в тикете |

```
Тикет
  → IE + классификация (summary, systems, priority, meta_category - Pydantic + field_validator)
  → hybrid RAG по runbook'ам и примерам из train (Chroma + BM25 + RRF)
  → генерация плана suggested_steps (grounded в KB)
  → критик + до 2 rework
  → ghost-check цитат
  → judge (на eval)
```

## Оценка

Прогон: `python eval.py --limit 15` (с judge), ~70 с/тикет.

| Метрика | Значение |
|---------|----------|
| Category accuracy | **9/15 = 60%** |
| Judge score (mean) | **0.57** |
| Judge pass (≥ 0.5) | **9/15 = 60%** |
| Steps supported (judge) | **14/15 = 93%** |
| Critic ok | **8/15 = 53%** |
| Grounded (critic ok + 0 ghost) | **8/15 = 53%** |
| Ghost-цитаты | **0** |
| Critic reworks (mean) | **1.13** |

**Оговорка про gold.** 25 исходных классов датасета схлопнуты в 9 meta-категорий через `label_map.json`. На практике границы размыты: много тикетов с gold=`other`, а модель уводит в `software` / `access` / `incident`. На части примеров разметка выглядит спорной - модель попадает в «логичную» категорию, а метрика считает промах. Поэтому **60% по category accuracy - нижняя оценка**, а **93% steps supported** ближе отражает, насколько полезен план действий.

## Где пайплайн ошибался

### 1. Сразу неверная категория - дальше всё поплыло (кейс #2)

**Вход:** «Подскажите, с кем поговорить про отчёт АС Договор - Проекты для удаления из СПС. Кто отвечает за отчёт, кто проверит корректность?»

**Gold:** `other` → **модель:** `software`

Summary в целом нормальный («консультация про ответственных за отчёт»), но из‑за `software` RAG ушёл в `software__0`, `software__1` - runbook про установку ПО и ошибки. Дальше цепочка ломается:

- **Шаг 1:** «уточните версию, ОС, скриншот ошибки» - в тикете нет ошибки, только вопрос про контакты
- **Шаг 4:** эскалация в L2, но по сценарию troubleshooting, а не «найти владельца отчёта»

Judge: **0.0**, critic: 2 rework, не прошёл. Типичный каскад: **ошибся в категории → не те чанки KB → план не про тот запрос**.

---

### 2. Категория верная, но шаги мимо (кейс #5)

**Вход:** «Для МФУ WC 6515 нужен пурпурный картридж, который сбоку вставляется, большой»

**Gold:** `hardware` → **модель:** `hardware` ✓

Классификация и summary («запрос картриджа для МФУ WC 6515») - ок. Проблема дальше, на этапе RAG + плана:

- **Шаг 2:** «проверить уровень тонера, очередь печати, замятие» - это из общего runbook про **неисправность** принтера, а в тикете просто **заказ расходника**
- Critic два раза просил переделать, не помогло - так и осталась диагностика вместо «оформить поставку картриджа»

Judge: category ✓, но score **0.5** - «категория верна, runbook общий, конкретный запрос на картридж не учтён». Здесь модель **не промахнулась в классе**, но **шаги** всё равно бесполезны оператору.

## Вывод

**Классификация** - главное слабое место: страдает категория `other` и пограничные пары (`account`/`access`, `request`/`hardware`, `workplace`/`software`). Хочется либо дообучить классификатор на train, либо пересмотреть первичную разметку / правила `label_map`.

**План действий (RAG + suggested_steps)** - скорее понравилось: steps supported 93%, ghost-цитат 0, шаги с цитатами из KB, критик реально включается (rework в ~55% кейсов). Critic и judge расходятся: критик придирается к цитатам, judge чаще режет за неверную категорию. Но иногда вывод модель слишком шаблонизирован из-за общих runbook, тут может помочь расширениие базы знаний для RAG
